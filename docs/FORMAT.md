# 格式逆向笔记

> 这份文档记录的是**实测得到**的结构，不是官方规格。凡是标了「推测」的地方都还没验证。
> 所有数值都是**大端序（big endian）**，除非另外说明。

## 1. 文件总览

```
游戏目录/
├── ac6recomp.toml        运行时配置（语言 / 区域）
```

`DATA.TBL` 自身是**明文**，可以直接读写。但它引用的数据在 PAC 里是压缩的。

## 2. DATA.TBL

### 2.1 头部

| 偏移 | 类型 | 含义 |
|---|---|---|
| `0x00` | u32 | 记录数（本项目为 **926**） |
| `0x04` | u32 | 未知，观察值恒为 0 |

### 2.2 记录（每条 16 字节）

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| `+0x00` | u32 | `flags` | 见下 |
| `+0x04` | u32 | `offset` | 在所属 PAC 中的字节偏移，`0x2000` 对齐 |
| `+0x08` | u32 | `comp_size` | PAC 中实际占用的字节数 |
| `+0x0C` | u32 | `uncomp_size` | 解压后的字节数 |

### 2.3 flags 位定义

| 位 | 掩码 | 含义 |
|---|---|---|
| bit 16 | `0x00010000` | 数据经过 mode-1 压缩 |
| bit 24 | `0x01000000` | 数据存放在 `DATA01.PAC`（为 0 则在 `DATA00.PAC`） |

观察到的实际取值：`0x00010000`（压缩 / DATA00）、`0x01010000`（压缩 / DATA01）。
**未压缩**的记录在本项目里没有出现，但 `0x00000000` 和 `0x01000000` 应该是合法的。

> ⚠️ bit 24 在读取时**不可全信**。某些重打包版本会出现偏移与 flags 不一致的情况，见 [§3.3](#33-读取策略两个-pac-都试)。

### 2.4 记录号 = 压缩垫索引

**这条极其重要**：压缩用的 XOR 垫依赖记录的**序号**（`DATA.TBL` 中的下标），不是 PAC 内偏移。
所以你不能把一条记录的数据搬到另一条的位置而不重新压缩。

## 3. 压缩（"mode-1"）

### 3.1 算法

```
压缩：  data ──raw deflate(-15)──> comp ──XOR pad──> 存进 PAC 的字节
解压：  存进 PAC 的字节 ──XOR pad──> comp ──inflate(-15)──> data
```

- `deflate` 用 **raw** 模式，窗口位 `-15`（没有 zlib 头、没有 adler32）
- `inflate` 必须传 `-15`，否则报 `incorrect header check`

### 3.2 XOR 垫从哪来

垫来自 **π 的十六进制小数展开**（不是十进制）：

```
π = 3.243F6A88 85A308D3 13198A2E 03707344 ...
```

按 32 位切分成字（word）数组 `W`，第 k 个 32 位字记作 `W[k]`。

对记录号 `idx`：

```python
i = idx % 256
pad = struct.pack(">II", W[2*i + 1], W[2*i + 2])   # 8 字节
pad = (pad * ceil(n / 8))[:n]                       # 平铺到长度 n
```

即：取第 `2i+1` 和 `2i+2` 个 32 位字，拼成 8 字节，然后**循环平铺**覆盖整个压缩流。

`idx % 256` 说明引擎里只有 256 个槽位的垫表，循环复用。

生成 `W` 的代码在 [`scripts/ac6lib.py`](../scripts/ac6lib.py) 的 `pi_words()`。本项目用高精度 `Decimal` 反三角函数算到 4200 位十六进制（足够覆盖 `2*255+2 = 512` 个 word）。

### 3.3 读取策略：两个 PAC 都试

初版实现按 flags 决定去哪个 PAC 读，结果 **797 条解压错位**（能解压但长度不对，或者直接抛异常）。

**正确做法**：

```python
for pac in (DATA00, DATA01):
    raw = pac[off:off+comp_size]
    try:
        data = inflate(xor(raw, pad(idx))) if compressed else raw
    except zlib.error:
        continue
    if len(data) == uncomp_size:   # ← 用长度校验，这是唯一可靠的判据
        return data
```

写入时才用 flags 判归属，并且要 `assert` 一下。

## 4. FHM 容器

### 4.1 头部

| 偏移 | 类型 | 含义 |
|---|---|---|
| `0x00` | 4 字节 | 魔数 `"FHM "`（注意尾部空格） |
| `0x04` | u32 | 未知 |
| `0x08` | u32 | 未知 |
| `0x0C` | u32 | 未知 |
| `0x10` | u32 | 子块数量 `nof` |
| `0x14` | u32 × nof | 子块偏移表（**相对于容器起始**） |
| `0x14 + 4*nof` | u32 × nof | 子块尺寸表（同序） |
| ... | bytes | 子块数据区 |

### 4.2 解析与替换

解析：

```python
nof = u32(d, 0x10)
offs  = [u32(d, 0x14 + 4*i)         for i in range(nof)]
sizes = [u32(d, 0x14 + 4*nof + 4*i) for i in range(nof)]
```

替换一个子块（**追加式**，不覆盖原字节）：

```python
new_off = align_up(len(d), 0x1000)
d += b"\x00" * (new_off - len(d))
d += new_payload
write_u32(d, 0x14 + 4*i,           new_off)
write_u32(d, 0x14 + 4*nof + 4*i,   len(new_payload))
```

代价：容器只增不减。本项目里一个包可能膨胀 10–30 MB。

### 4.3 层级结构（过场包）

```
package (FHM, nof = 26 / 55 等)
├── c0  (FHM)
│   ├── c0.0  NFICSCEN  —— 场景/镜头元数据
│   ├── c0.1  ... 
│   ├── c0.2  语言容器 (FHM, nof = 7)
│   │   ├── [0] 日本語   = FHM[ CAPT, 排版表, 图集FHM ]
│   │   ├── [1] English  = FHM[ CAPT, 排版表, 图集FHM ]   ← 汉化组改的是这里
│   │   ├── ...
│   │   └── [6]
│   └── c0.3  ...
├── c1 ...
├── c4  字体（日文）
├── c5  字体（英文 / 汉化后 = 中文）
├── c18 / c19 ...  更多语言容器
└── c22 / c23      纯场景数据（不含 CAPT）
```

> 不同包的 chunk 数量不一样（26 / 55 / …），**不要硬编码**，用 `nof` 遍历。

## 5. 语言容器判定

一个 FHM 满足以下**全部**条件，就是语言容器：

1. `nof` 在 2 ~ 12 之间
2. **每一个**子块自身的魔数都是 `FHM `
3. **每一个**子块的 `chunk0` 前 4 字节是 `CAPT`

```python
def is_lang_container(b):
    r = fhm_chunks(b)
    if not r: return 0
    nof, offs, sizes = r
    if not (2 <= nof <= 12): return 0
    kids = [b[offs[i]:offs[i]+sizes[i]] for i in range(nof)]
    if not all(k[:4] == b"FHM " for k in kids): return 0
    for k in kids:
        rr = fhm_chunks(k)
        if k[rr[1][0]:rr[1][0]+4] != b"CAPT": return 0
    return nof
```

**为什么条件要这么严**：早期审计脚本只判断"子块全是 FHM"，结果把顶层 26 / 55 个子块的**整个包**误判成语言容器，得出一堆假阳性。

### 5.1 槽位顺序

```
[0] 日本語      ← 目标（写入这里）
[1] English     ← 汉化后 = 中文（来源）
[2] Français
[3] Italiano
[4] Deutsch
[5] Español
[6] 未知/占位
```

判断依据：中日文槽的 NTXR 纹理是 **2048×256**，其他语言只有 **256×256**。

## 6. 字幕语言块

一个语言块（语言容器里的一个槽）是 `FHM` 容器，固定三块：

```
语言块 FHM
├── chunk0   CAPT        32 字节头
├── chunk1   排版表       47 × 16 字节（未使用项填 0xFF）
└── chunk2   图集 FHM[8]  见 §6.2
```

> ⚠️ 排版表是 **CAPT 的兄弟块**，不是 CAPT 的内部数据。早期的理解在这里搞错过一次。

### 6.1 CAPT 头（32 字节）

| 偏移 | 类型 | 含义 |
|---|---|---|
| `0x00` | 4 字节 | 魔数 `"CAPT"` |
| `0x04` | u32 | 版本？观察值较小 |
| `0x08` | u32 | 头部尺寸？观察值为 32 |
| `0x0C` | u32 | 条目数？ |
| `0x10` | 16 字节 | 剩余头部，内容未明 |

### 6.2 排版表判定

排版表是 `n × 16` 字节，每条前 4 字节若为 `FF FF FF FF` 视为**空条目**：

```python
used = sum(1 for i in range(len(tab)//16)
           if tab[i*16:i*16+4] != b"\xff\xff\xff\xff")
```

**这个数字是区分"字幕包"和"字体包"的关键判据**，见 §7。

### 6.3 图集（chunk2）

```
图集 FHM
├── k0   52 字节  头
├── k1   1504 字节 = 47 × 32  每条含 {长度, 偏移, 序号}
├── k2   2296 字节  字距/度量
├── k3   1536 字节  字距/度量
├── k4   96 字节
├── k5   3062 字节
├── k6   NFH\0  字体名（如 musen_US, Regular）
└── k7   NTXR   纹理
```

### 6.4 纹理

- 格式：**DXT5**
- 尺寸：CJK = **2048 × 256**；其他语言 = **256 × 256**
- 像素数据从 NTXR 头之后 **4096 字节**开始
- 布局：**Xbox 360 tiled**（32×32 block tile）

> ❗ **未能完全解码**。用标准的 32×32 tile 反变换后解码出来仍是噪声，说明还有一层 swizzle 或格式差异没搞对。这是"改翻译"路线的最大障碍。

### 6.5 为什么不能直接改文本

对整个资源库做过四种编码的明文扫描：

| 编码 | 命中数 |
|---|---|
| UTF-8 | 0 |
| GBK | 0 |
| UTF-16 LE | 0 |
| UTF-16 BE | 0 |

**没有任何中文明文。** 字幕是"字形索引 → 图集取位图"，不是字符串。
改一句翻译 = 重画字形 + 重编码 DXT5 + 处理 tiled 布局。成本远高于收益。

## 7. 字体包

`#467` ~ `#472` 是**纯字体资源**，特征：

- 结构是 `FHM[ CAPT, 排版表, 图集FHM ]`，但**不是语言容器**（没有 7 槽包装）
- CAPT 的排版表条目**全部为空**
- 只含字形图集，不含任何字幕内容

汉化组替换了 `#467`（1024×256 中文大图集），`#468`~`#472` 是配套小字模（256×256）。
**不要动这几个包**，重复处理会导致方块字。

## 8. ISO 定位（取原版基线用）

XDVDFS 布局：

| 项目 | 偏移 / 规则 |
|---|---|
| 卷描述符 | `0xFD90000` |
| 根目录 | `0xFDA0000` |
| 根目录 sector | 从卷描述符 `+0x14` 读 u32 |
| 根目录 size | 从卷描述符 `+0x18` 读 u32 |
| 任意文件 | `offset = sector × 2048` |

本项目使用的 ISO（USA, Japan 双版）里两个数据堆的位置是**硬编码**的：

| 堆 | 偏移 | 大小 |
|---|---|---|
| DATA00.PAC | `0x06197F800` | 2,266,267,648 |
| DATA01.PAC | `0x154E3A000` | 664,141,824 |

> 换一个 ISO dump，这两个偏移**必须重新推导**。方法：搜 `DATA.TBL` 里某条记录的 `comp_size` 对应的数据特征，或者从根目录遍历得到文件 sector。
